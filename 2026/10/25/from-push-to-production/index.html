从「推完 GitHub 就结束」到「push 即上线」

发表于2026-10-25|更新于2026-10-25|工程化
|浏览量:

我以前做个人项目的完整流程是：写代码 → git push → 结束。代码躺在仓库里，从没想过「部署」「服务器」「上线」这些词，也没觉得缺了什么——直到这次从零搭了这个博客（你现在正在看的这个站），被逼着把整条链路走了一遍。

这篇是我给自己写的工程化总结，全部内容来自亲手踩过的坑。有个很妙的巧合：你正在读的这篇文章，本身就是文中那套流程的最新一次运行产物。

一、全景图：我以前缺的是哪几环

以前：写代码 → push → 结束。代码只有我和 GitHub 服务器知道。

现在：

工程化就是这条链：每一步自动化、可重复、可追溯。我以前缺的是「构建 → 部署 → 托管」这后三环，现在它们全自动了，我的日常仍然只有 git push。

二、构建、部署、托管：三个经常混着说的词

一句话分工：

  • **托管（Hosting）**是「房子」——网站长期住的地方，7×24 在线、随时响应浏览器
  • 部署（Deploy）是「搬家上架」这个动作——把新构建的产物送进房子的那次传输
  • CI/CD 是「自动化的规矩」——让「构建 + 部署」在 push 之后自动发生

三者的时间形态完全不同：托管是常驻的；部署是瞬间动作，每次发布发生一次；CI/CD 平时不存在，只有 push 那一刻 GitHub 才临时起一个容器跑几分钟，跑完销毁。

概念 我项目里的实体 时间形态
托管 GitHub Pages（指向 gh-pages 分支） 常驻
部署 把产物推到 gh-pages 分支 每次发布一次
CI/CD .github/workflows/deploy.yml push 时临时出现

三个容易混的点，我都亲测过：

  1. CI 和 CD 是两件事。CI = 持续集成（自动构建 + 验证），CD = 持续部署（自动发布）。很多流水线只有 CI 没有 CD，发布留给人工按钮——我的 deploy.yml 是全自动的，两个都有。
  2. 部署可以没有 CI/CD。我项目里其实留着两条部署通道：npm run deploy 手动部署，和 Actions 自动部署。自动化的价值不是「能部署」，而是部署这个动作从日常里消失了。
  3. 托管和部署是两个阵营。部署工具负责「送」，托管平台负责「住」，中间用约定衔接（「gh-pages 分支的内容就是网站」）。所以以后换托管平台（比如迁到国内 CDN），只改部署那段，构建、源码、写作流程全都不动——流水线的每一段都是可替换的模块。

开个餐厅类比：托管是商铺，构建是后厨做菜，部署是把新菜端上柜台，CI/CD 是定下的规矩——每次进货（push），后厨自动做完菜自动上柜，我连厨房都不用进。

三、上线：从「大事件」变成「日常动作」

上线 = 三个动作的合称：发布（决定哪个版本是正式版，如打 tag）+ 部署（送到生产环境）+ 开门营业（流量放进去）。

我的博客在「开启 GitHub Pages 那一刻」就完成了第一次上线，之后每次 push 都是一次微型上线。这里有个关键的认知转变：

传统开发是憋几个月、挑好日子、通宵上线、祈祷不出事——因为上线成本高风险大，才需要仪式感。流水线让上线变成例行公事后，上线频率越高、单次改动越小，风险反而越低（出了问题立刻知道是哪个改动引起的）。这就是持续交付的核心：产品永远处于可上线状态。

以后做真正带后端的产品，上线要比博客多补这些功课，先存档备用：

环节 为什么需要
环境分层（开发→测试→生产） 上线 = 发布到生产环境；测试环境先验证一遍，别把 bug 直接塞给用户
域名 + HTTPS 证书 正式产品的门面和安全底线
密钥走环境变量/Secrets 硬编码进代码 = 泄漏倒计时
监控与日志 服务挂了要自己第一时间知道，而不是用户告诉你
回滚方案 新版本出问题，一条命令退回上一版
合规（国内要备案） 解析到国内服务器/CDN 的法律要求

顺便记录不同产品形态的「上线」：静态站 = push 自动上线（已会）；Web 应用 = 前端托管 + 后端服务器 + 数据库三件套；小程序/App = 提交平台审核 → 通过后发布版本（上线被平台把关）；桌面软件 = 发安装包 + 自动更新通道。形态越重上线越复杂，但「版本 → 构建 → 部署 → 对外」的骨架完全一样。

四、静态 vs 动态：两种架构的分水岭

先纠正一个误区：页面上有动画、有交互 ≠ 动态网站。真正的分界线是：

访客请求内容的那一刻，服务器上有没有程序在为他现场计算？

  • 静态：服务器里只有预先生成好的文件，谁来都拿同一份。代码只在两个地方运行过——我电脑上（构建时）和访客浏览器里（前端 JS）。服务器只负责搬文件。
  • 动态：服务器上住着一个常驻程序（我平时写的那种 Node/Java/Python 服务），每个请求进来都现场跑一遍——查库、拼页面、判断权限——算完才回复。

干活时机不同，是两种架构一切差异的总根源。 全面对照：

维度 静态（本博客） 动态（我平时的项目）
服务器上有什么 纯文件 常驻程序 + 数据库
内容生成时机 构建期，一次生成 运行期，每请求一次
访客看到的 所有人完全相同 可因人而异
本地开发 一个预览命令 要跑后端 + 数据库
部署 传文件，秒级 部署进程、配环境、守护
费用 托管免费 服务器租金
攻击面 极小（没有可入侵的程序） 大（注入、越权、补丁）
数据写回 原生没有 天然支持
挂了会怎样 几乎不会挂 程序崩 = 全站不可用
扛并发 CDN 天然分流 要自己搞负载均衡

最有启发的案例是我自己做的私有文章——同一个需求，两种架构在不同时机解决：

  • 动态站（运行期判断）：if (user === owner) 显示全部 else 只查公开，每次请求判断一次
  • 静态站（构建期过滤）：构建时直接跳过 published: false 的文章，私有内容压根不进入产物——不需要判断，因为公开世界里根本没有这份数据

而我的博客其实大量采用了「静态打底 + 借用外部动态服务」的组合（这套打法叫 JAMstack）：评论借 GitHub 的接口、写作后台借 DecapBridge 的登录和 GitHub 的 API、统计借第三方脚本、搜索借构建期生成的索引文件在访客浏览器里算。用别人的动态服务补静态的短板，同时让「自己的服务器」保持为零——个人项目性价比最高的架构。

三句话判断法：内容对所有人一样、单向发布 → 静态；因人而异、用户要写数据 → 动态；介于两者 → 静态打底 + serverless 函数补动态。

五、踩坑实录（比成功更有价值）

案例 现象 学到的心法
npm 装依赖报 Cannot read properties of null 依赖解析崩了 已知 bug → 清状态重装（删 node_modules），别恋战
部署中途报错 spawn 崩了 网络抖动 → 先重试再排查，别过度反应
改了样式线上没变化 看到旧页面 CDN/浏览器缓存 → 强刷、缓存穿透参数验证，再下结论
后台发布 403 权限报错 用 API 实测令牌真实权限——界面显示的权限信息把我误导过，实测才作数
git push 被拒 fast-forward 错误 后台和本地是两个写者，push 前先 git pull（我配了 pull.rebase）

通用心法：先读报错原文 → 缩小变量 → 实证（curl / API / 最小复现）而不是猜 → git 保证一切可回滚。

六、Git 的角色升级

以前 Git 对我 = 备份工具。这次它干了四件事：

  1. 触发器：push 是流水线的扳机
  2. 内容数据库：文章就是仓库里的文件，网页后台改的其实是仓库
  3. 发布通道：main 放源码、gh-pages 放成品——分支成了「版本号持续滚动的发布存档」
  4. 协作的缩影：后台和我本地是两个写者，「push 前先 pull」就是团队开发的冲突管理日常

七、认证与密钥三件套

  • SSH 密钥：私钥在本机、公钥在 GitHub，不传密码就能证明「是我」。坑：git 和系统 ssh 可能用不同的密钥库，排查时别想当然。
  • OAuth：不把密码交给第三方网站，而是「授权」它代表我操作。GitHub 的 OAuth 必须有服务端参与令牌交换，所以需要 DecapBridge 这类「认证中转」。
  • PAT（个人访问令牌）纪律：细粒度令牌、只授权单个仓库的最小权限、设过期时间、不进代码不进聊天（我贴出来过一次，处理方式就是作废重发）、权限可疑时用 API 实测。

八、术语速查表

术语 一句话 在我项目里
构建 源码 → 可运行产物 hexo generate → public/
部署 把产物放到在线服务器 push 到 gh-pages
托管 常驻在线的文件服务 GitHub Pages
CI/CD push 后自动构建部署 .github/workflows/deploy.yml
CDN 边缘节点就近加速 （待接入）
DNS 域名 → IP 的翻译 （待买域名）
OAuth 授权第三方代替操作 DecapBridge 登录
PAT 个人访问令牌 交给中转服务的仓库钥匙
CMS 网页内容管理系统 /admin（Decap）
静态/动态站 预生成文件 vs 现场计算 本博客 vs 我以前的 Web 项目

结语

我以前的项目是「程序在运行期干活，推完 GitHub 就没人运行它了」；这个博客教会我另一种范式——把活儿挪到构建期干完，把运行期简化到零。两种范式没有高下，聪明的做法是让它们各干各的活。

最后再强调一遍开头的巧合：这篇文章从 hexo new 到出现在你面前，经过的正是第一节的那条流水线。工程化不是背概念，是把这条链亲手搭一遍——搭完之后，每一篇新文章、每一个新项目，都只是在重跑它。
